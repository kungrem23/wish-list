# Вишлист

Владелец создаёт список с датой праздника или без даты и отправляет друзьям ссылку. Вошедшие пользователи по ссылке могут бронировать подарки и отменять свои брони. До архивации владелец видит только карточки подарков без данных о бронях. В архиве можно исправить итоги и перенести видимые неподаренные позиции в новый список.

## Тайный Санта

1. В разделе **Тайный Санта** создайте событие. Укажите название, дату обмена, часовой пояс, бюджет с валютой и правила. Бюджет служит ориентиром. Организатор может сам участвовать в обмене.
2. Скопируйте общую ссылку и отправьте её участникам. После входа или регистрации они вернутся на страницу приглашения и смогут подать заявку. Организатор одобряет и отклоняет заявки и может исключать других участников. При перевыпуске ссылки прежняя перестаёт действовать.
3. Участник может привязать свой активный вишлист или создать новый. Форма по умолчанию предлагает список без даты. Если выбрать «С датой», форма подставит дату обмена и часовой пояс события. Привязка необязательна, а у списка свои сроки и правила архивации.
4. Запустите жеребьёвку, когда одобрены хотя бы два участника. Каждый дарит и получает по одному подарку. Назначение самому себе исключено, взаимные пары допустимы. В группе из двух или трёх человек дарителя можно вычислить по своему назначению.

Участник видит имя своего получателя и его привязанный вишлист. Имя дарителя остаётся скрытым и в архиве. Организатор видит заявки, состав и своё назначение, если участвует. Карточки и фотографии открываются через событие, пока доступны и событие, и список получателя. Если список закрывается раньше события, имя получателя остаётся видно. Брони через событие и по обычной ссылке конкурируют за одну карточку. Доставку и обмен участники организуют самостоятельно.

В первой и каждой повторной жеребьёвке участвуют все одобренные участники. Организатор меняет состав отдельно в разделе **Заявки и состав**. Кнопка **Исключить** сразу отзывает назначения с участием этого человека. После изменения состава проведите новую жеребьёвку, чтобы распределить подарки между всеми текущими участниками. Если у кого-то уже есть бронь для текущего получателя, приложение попросит подтверждение. Учитываются текущие брони и через событие, и по обычной ссылке. После успешной пережеребьёвки действуют новые назначения, а существующие брони остаются в разделе **Брони и история**. Там их можно отменить, пока это допускают правила списка.

Событие переходит в архив с начала следующего календарного дня в своём часовом поясе. В архиве события участник видит имя получателя последнего раунда. Доступ к списку через событие закрывается, а сам список продолжает жить по своим правилам. Бронь можно отменить в разделе **Брони и история**, пока открыт список. Для события без раунда отображается статус **Жеребьёвка не проведена**.

## Запуск через Docker Compose

Из корня репозитория запустите приложение.

```sh
docker compose up -d --build --wait
```

Откройте [http://127.0.0.1:8080](http://127.0.0.1:8080). Compose поднимает PostgreSQL и SeaweedFS, применяет новые миграции перед запуском API и раздаёт собранный фронтенд через Nginx. База и фотографии хранятся в отдельных томах и сохраняются после `docker compose down`. Архиватор запускается каждый час и удаляет неиспользуемые фотографии и аватарки. Для ручного запуска выполните `docker compose exec -u nobody archive wishlist-archive`.

Для другого порта задайте `WISHLIST_PORT` в `.env` в корне репозитория. Перед первым запуском там же можно задать `POSTGRES_PASSWORD`, `S3_BUCKET`, `S3_ACCESS_KEY_ID` и `S3_SECRET_ACCESS_KEY`. По умолчанию используются настройки для локальной разработки. Compose создаёт собственную базу и публикует только порт веб-интерфейса на `127.0.0.1`.

## Локальный запуск без Compose

Понадобятся Go 1.25+, Node.js 22.12+ и запущенный PostgreSQL с поддержкой ICU и клиентом `psql`. ICU нужен для сортировки названий подарков по правилам русского языка.

1. Создайте пустую базу `wishlist` и укажите строку подключения. Примените миграции по порядку номеров.

   ```sh
   export DATABASE_URL='postgresql://wishlist:password@127.0.0.1:5432/wishlist?sslmode=disable'
   for migration in migrations/*.sql; do
     psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "$migration" || break
   done
   ```

   Замените пользователя и пароль на свои. Для существующей базы применяйте новые файлы миграций по порядку номеров. Миграция `005_open_wishlists_and_profiles.sql` сохраняет даты, токены, брони, историю и ссылки на фотографии. Миграция `006_wishlist_avatars.sql` добавляет аватарки вишлистов.

2. Для загрузки фотографий подключите локальное S3-хранилище. Например, запустите SeaweedFS в Docker. Контейнер создаст закрытый бакет, а том сохранит файлы между перезапусками. [Документация SeaweedFS](https://github.com/seaweedfs/seaweedfs#docker)

   ```sh
   export S3_ENDPOINT='http://127.0.0.1:8333'
   export S3_BUCKET='wishlist-photos'
   export S3_ACCESS_KEY_ID='wishlist-local'
   export S3_SECRET_ACCESS_KEY='replace-with-a-local-password'
   docker run -d --name wishlist-s3 \
     -p 127.0.0.1:8333:8333 -v wishlist-s3-data:/data \
     -e S3_BUCKET \
     -e AWS_ACCESS_KEY_ID="$S3_ACCESS_KEY_ID" \
     -e AWS_SECRET_ACCESS_KEY="$S3_SECRET_ACCESS_KEY" \
     chrislusf/seaweedfs:4.53
   ```

   Для уже работающего S3-совместимого хранилища укажите его адрес и данные доступа к существующему закрытому бакету. API использует path-style адресацию. Если хранилище настроено на другой регион, задайте `S3_REGION` вместо значения по умолчанию `us-east-1`. Без `S3_ENDPOINT` форма работает без загрузки файлов.

3. В том же терминале запустите API из корня репозитория. По умолчанию он слушает `127.0.0.1:8080`. Адрес можно изменить через `HTTP_ADDR`.

   ```sh
   COOKIE_SECURE=false go run ./cmd/api
   ```

4. Во втором терминале запустите фронтенд.

   ```sh
   cd frontend
   npm ci
   npm run dev
   ```

   Откройте [http://localhost:5173](http://localhost:5173). На странице входа можно создать аккаунт. Для проверки ссылки войдите вторым аккаунтом в другом профиле браузера или приватном окне. Vite проксирует запросы `/api` на порт 8080.

Для развёртывания соберите фронтенд командой `npm run build` из `frontend`. Раздавайте `frontend/dist` через HTTPS с возвратом `index.html` для маршрутов SPA. На том же домене проксируйте `/api/` к Go API с исходным заголовком `Host`. При HTTPS используется значение `COOKIE_SECURE` по умолчанию.

Для загрузки фотографий разрешите на прокси тело запроса до 26 МиБ. API читает и записывает объекты в бакете, а архиватору с теми же настройками S3 нужен также доступ на удаление объектов с префиксом `gift-photos/`.

За обратным прокси укажите его IP в `TRUSTED_PROXY_IP`, чтобы лимит попыток учитывал адрес клиента. Прокси должен перезаписывать `X-Real-IP` фактическим адресом клиента. Ограничьте доступ к порту API прокси-сервером. При прямом подключении оставьте `TRUSTED_PROXY_IP` пустым.

Вход и регистрация совместно допускают до 30 попыток в минуту с одного IPv4-адреса или IPv6-подсети /64 и до 5 на один email. API ограничивает число параллельных операций входа и регистрации. При превышении лимита API возвращает `429`, при перегрузке — `503`. В обоих случаях `Retry-After` указывает время ожидания в секундах. Счётчики действуют в пределах одного процесса API. При регистрации проверяются 1 000 распространённых паролей из словаря Dropbox zxcvbn v4.4.2.

## Архивация

Из корня репозитория с тем же `DATABASE_URL` запустите один проход вручную. Передайте те же переменные `S3_*`, чтобы проход также удалял из хранилища файлы, которые больше не привязаны ни к подарку, ни к профилю, ни к списку, и файлы от неудавшихся загрузок.

```sh
go run ./cmd/archive
```

Для ежечасного запуска соберите бинарник и укажите его в cron. Команда обрабатывает все просроченные списки, включая пропущенные, и завершает работу с ненулевым кодом при ошибке.

```sh
go build -o /opt/wishlist/wishlist-archive ./cmd/archive
```

Пример записи для `crontab -e` на машине с доступом к PostgreSQL.

```cron
0 * * * * /opt/wishlist/run-archive >> /opt/wishlist/archive.log 2>&1
```

Пример исполняемого файла `/opt/wishlist/run-archive`. Укажите в нём строку подключения к той же базе, что использует API, и переменные `S3_*`, если настроено хранилище. Ограничьте доступ к файлу учётной записью службы.

```sh
#!/bin/sh
export DATABASE_URL='postgresql://wishlist:password@127.0.0.1:5432/wishlist?sslmode=disable'
exec /opt/wishlist/wishlist-archive
```

Для списка с датой редактирование заканчивается с начала дня праздника. Бронирование и доступ гостей к списку и его фотографиям закрываются с начала следующего календарного дня в часовом поясе списка. Это происходит сразу при наступлении срока. Фоновая архивация позже фиксирует итоги и переносит брони в личную историю. Список без даты открыт для редактирования и бронирования до ручной архивации. Пока список можно редактировать, владелец может добавить, изменить или убрать дату.

Владелец может архивировать любой открытый список кнопкой **Архивировать** или запросом `POST /api/v1/wishlists/{id}/archive`. Повторный запрос для уже архивированного списка возвращает `204`. Ручная и автоматическая архивация используют общую блокировку списка и одну транзакцию для итогов, истории и `archived_at`. Владелец может исправлять итоги и копировать неподаренные позиции в список с датой или без даты.

У аккаунта может быть до 50 списков, включая архив. В одном списке может быть до 100 карточек, включая скрытые. При достижении квоты создание и копирование возвращают `409`. Имеющиеся данные доступны постранично. Эндпоинты списков, карточек, подписок, броней и истории возвращают до 50 записей и передают курсор следующей страницы в заголовке `X-Next-Cursor`. Передайте его как параметр `after` следующего запроса. В ответах со списками `gift_count` учитывает все активные подарки, а для архива владельца — все карточки, видимые в архиве.

## Профили и подписки

Маршрут `/users/:id` открывает профиль после входа. Из открытого вишлиста в тот же экран можно перейти по ссылке владельца. В общей части видны имя, аватар, описание до 1000 символов, размеры и возраст. Email и полная дата рождения доступны владельцу в настройках. Активные списки в профиле видны всем вошедшим пользователям. Кнопка с аватаркой в правом верхнем углу открывает меню с именем, email, переходом в настройки профиля и кнопкой **Выйти**.

Кнопки **Подписаться** и **Отписаться** сразу меняют связь в одном направлении. В разделе **Подписки** есть вкладки **Я подписан** и **Подписчики** со ссылками на профили. Подписка сохраняет профиль во вкладке **Я подписан**, откуда удобно открывать новые вишлисты.

В настройках можно сохранить до 10 адресов доставки. Для каждого нужны название до 80 символов и адрес до 500. Владелец видит их всегда, другой пользователь — только при взаимной подписке. После отписки адреса пропадают при следующем запросе профиля, включая вход по ссылке на список. Списки подписок и Тайный Санта не возвращают адреса.

Для аватарок профиля и вишлиста подходят JPEG, PNG и WebP до 5 МиБ и 8192 пикселей по каждой стороне. Аватарку списка можно добавить, заменить или удалить в **Настройках** списка, пока он доступен для редактирования. Она видна на карточке списка и в его заголовке. API применяет к аватарке те же правила доступа, что и к списку, в том числе через Тайного Санту.

Аватарки хранятся в том же закрытом S3-бакете, что и фотографии подарков. При неудачной замене сохраняется прежняя аватарка. Архиватор удаляет непривязанные объекты старше часа и сохраняет файлы, на которые ссылается подарок, профиль или вишлист.

## API

Все маршруты в таблице начинаются с `/api/v1` и требуют входа.

| Маршрут | Назначение |
| --- | --- |
| `POST /wishlists`, `PUT /wishlists/{id}`, `POST /wishlists/{id}/copy` | При наличии даты передайте `holiday_date` и `time_zone`. Без даты оба поля можно опустить или передать как `null`. В ответе для списка без даты `close_at` равен `null`, а поля даты и пояса опущены. |
| `POST /wishlists/{id}/archive` | Архивировать открытый список владельца. Повтор возвращает `204`. |
| `GET /wishlists/{id}`, `GET /shared/{token}`, просмотр списка в Тайном Санте | Параметр `sort` принимает `priority` по умолчанию, `name` или `added`. Курсор действует для выбранной сортировки. |
| `GET /users/{id}`, `GET /shared/{token}/profile` | Общая часть профиля, `active_lists` и адреса при наличии доступа. Закрытая ссылка возвращает гостю `404`. |
| `PUT /users/{id}/follow`, `DELETE /users/{id}/follow` | Идемпотентная подписка и отписка. |
| `GET /me/following`, `GET /me/followers` | Исходящие и входящие подписки вошедшего пользователя. |
| `GET /me/addresses`, `POST /me/addresses`, `PUT /me/addresses/{id}`, `DELETE /me/addresses/{id}` | Чтение и изменение своих адресов. При сохранении передайте `label` и `address`. |
| `PUT /me/avatar`, `DELETE /me/avatar` | Загрузить одну аватарку полем `photo` в multipart или удалить текущую. Ответ содержит обновлённый профиль с `avatar_url`. |
| `PUT /wishlists/{id}/avatar`, `DELETE /wishlists/{id}/avatar` | Загрузить или удалить аватарку своего списка. Используйте multipart-поле `photo`. URL изображения возвращается в `avatar_url` при чтении списка. |
| `PUT /santa/events/{id}/applications/{user}` | Одобрить, отклонить или исключить участника. Передайте актуальную версию события и `status`. |
| `POST /santa/events/{id}/draw` | Провести жеребьёвку для всех одобренных участников. Передайте актуальную `version` и `confirm_round`, если сервер запросил подтверждение. |

## Модули и карточки подарков

- `internal/accounts` ведёт аккаунты, профиль и сессии. Случайный токен передаётся в HttpOnly cookie, в базе хранится его хеш.
- `internal/wishlists` управляет списками, карточками, активными бронями и итогами. Архиватор фиксирует видимость и исходный итог, переносит бронь в историю и закрывает список в одной транзакции.
- `internal/history` ведёт личные записи о бронях на момент закрытия. Текущий итог читается из `gifts.gifted` при каждом запросе, поэтому правка владельца видна в истории. Удаление записи меняет только `gift_history`.
- `internal/santa` ведёт события, заявки, состав и назначения. Маршруты начинаются с `/api/v1/santa/`. Миграция `004_secret_santa.sql` добавляет таблицы и ограничения. В базе хранится хеш приглашения, а сам токен API выдаёт при создании события и перевыпуске ссылки.

Запуск жеребьёвки блокирует строку события, проверяет срок и ожидаемую версию, читает текущий состав и сохраняет назначения в одной транзакции. Если для пережеребьёвки нужно подтверждение, сервер возвращает `409` с `confirm_round` и проверяет раунд и версию при повторном запросе. Маршруты списка, фотографий и брони проверяют текущее назначение и доступность события и списка на каждом запросе. Через `DELETE /api/v1/reservations/{gift}` автор может отменить бронь по правилам списка, в том числе после смены назначения. Для броней из события ответ со списком броней скрывает обычный токен ссылки на вишлист.

Ручное создание и редактирование используют один метод `wishlists.Store.SaveGift` с полями `title`, `description`, `product_url`, `price` и `priority`. Цена в рублях передаётся десятичной строкой с точкой, например `"1490.50"`, или `null`. Допустимы неотрицательные значения до 9 999 999 999,99 с точностью до двух знаков. В форме можно вводить точку или запятую. Приоритет принимает `high`, `normal` или `low`. Для существующих подарков цена пуста, а приоритет обычный. Те же поля передаются в JSON-части `card` при multipart-загрузке. При копировании цена и приоритет сохраняются.

База сортирует весь набор карточек до пагинации. По умолчанию сначала идут подарки с высоким приоритетом, затем с обычным и низким. Сортировка по имени учитывает кириллицу, сортировка по дате добавления показывает новые карточки первыми. ID определяет порядок при совпадении ключей.

Метод проверяет и сохраняет поля локально. Будущий адаптер импорта сможет принять URL и вернуть черновик `wishlists.Card`. После проверки пользователь отправит его через тот же сценарий сохранения. Ручная форма работает с любым обычным HTTP(S)-адресом и при недоступности площадки.

При создании или редактировании подарка можно прикрепить до пяти фотографий JPEG, PNG или WebP размером до 5 МиБ каждая и до 8192 пикселей по каждой стороне. При редактировании можно отметить фотографии для удаления. API выдаёт фото вошедшим пользователям с доступом к карточке. При копировании подарка из архива новый список использует те же файлы.

## Проверка

```sh
go test ./...
TEST_DATABASE_URL="$DATABASE_URL" go test ./... -count=1 -v
cd frontend && npm run build
```

С `TEST_DATABASE_URL` тесты применяют миграции в отдельных временных схемах PostgreSQL. Роль должна иметь право создавать схемы. Сценарии проверяют обновление схемы с существующими списками, бронями, историей и фотографиями, переход между списками с датой и без даты, копирование цены и приоритета, ручную и автоматическую архивацию, гонки с бронированием, закрытие доступа на границе `close_at` и сортировку нескольких страниц. Отдельно проверяются обе вкладки подписок, права на адреса при разных направлениях подписки и отзыв доступа после отписки.

Для запуска только интеграционных сценариев «Тайного Санты» выполните команду из корня репозитория.

```sh
TEST_DATABASE_URL="$DATABASE_URL" go test ./internal/httpapi -run '^TestPostgresSanta' -count=1 -v
```

Эти тесты проверяют заявки, приватность назначений и фотографий, гонки при изменении состава и запуске раунда, повтор запроса, откат при ошибке и закрытие в часовом поясе события. Отдельно проверяются предупреждения о бронях из обоих источников, отзыв доступа и отмена брони после смены получателя или исключения участника. Пережеребьёвка проверяется на полном составе одобренных участников.

Для проверок с настоящим S3 передайте адрес и настройки отдельного закрытого тестового бакета. Сценарии проверяют загрузку, закрытие доступа к фото, замену аватарок профиля и списка, сохранение прежних при сбое и удаление непривязанных объектов.

```sh
TEST_DATABASE_URL="$DATABASE_URL" TEST_S3_ENDPOINT="$S3_ENDPOINT" \
  S3_BUCKET="$S3_BUCKET" S3_ACCESS_KEY_ID="$S3_ACCESS_KEY_ID" \
  S3_SECRET_ACCESS_KEY="$S3_SECRET_ACCESS_KEY" go test ./... -count=1 -v
```
